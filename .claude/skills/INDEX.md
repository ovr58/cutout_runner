# .claude/skills/ — карта скилов (INDEX)

> **Карта вместо чтения десятков SKILL.md.** Одна строка на скил (триггер · группа).
> Правило consult-first (в `CLAUDE.md`): **перед действием свериться, нет ли подходящего
> скила** — найти его здесь по триггеру, затем открыть его `SKILL.md` и следовать ему.
> Любое добавление/переименование скила обновляет строку здесь **в том же изменении**
> (см. `writing-skills`).

Обновлено: 2026-09-04

## Planning & design

| Скил | Когда (триггер) |
| --- | --- |
| spec-intake | Новый проект из шаблона / нет `docs/TZ.md`+`SPEC.md`+`VISUALS.md`, а работа начинается / есть только референс «хочу как вот это» / генеральный план пишут без спеки — три входа, опросник, три артефакта, handoff со сменой модели |
| brainstorming | Неоднозначный/крупный запрос, выбор подхода — расширить пространство решений перед планом |
| writing-plans | Многошаговая задача / решения для ревью / работа продолжится в др. сессии — план по lifecycle |
| executing-plans | Есть одобренный план в `planning/active/` — исполнять по шагам, держать статус |
| writing-skills | Создаёшь/правишь `SKILL.md` — формат, триггер-описание, кросс-рефы, индекс |

## Domain modeling & architecture

| Скил | Когда (триггер) |
| --- | --- |
| grill-with-docs | План/спека ещё размыты — интервью по одному вопросу (само-ответ из кода), словарь → `CONTEXT.md`, необратимые решения → `docs/adr/`. До writing-plans; дополняет brainstorming |
| domain-modeling | Термин двоится / решение надо зафиксировать при уже ясном плане — вести единый язык в `CONTEXT.md` и необратимые решения в `docs/adr/`. Референс-дисциплина для grill-with-docs |
| codebase-design | Проектируешь/переделываешь модуль — глубокий модуль (узкий стабильный интерфейс, сложность спрятана) на чистых швах; словарь depth/seam/interface. Дополняет ponytail (глубина ≠ золочение) |
| improve-codebase-architecture | Периодическое ТО архитектуры — скан git-churn на «утолщения» (shallow→deep), deletion-test, HTML-отчёт в OS-temp, затем грилл выбранного. Спавн под §2 |
| research | Вопрос надо разобрать по первоисточникам, не по памяти — свидетельства + цитируемая Markdown-заметка. Default inline; спавн под §2 |

## Subagent orchestration (под cost-discipline)

| Скил | Когда (триггер) |
| --- | --- |
| subagent-driven-development | Тянет спавнить субагента — гейт: inline или спавн? как заскоупить и какая модель |
| dispatching-parallel-agents | Реально независимые потоки И спавн уже оправдан — корректный fan-out под cost-discipline |

> Эти два скила **гейтят** спавн под дисциплину затрат (`docs/WORKING_RULES.md` §2):
> по умолчанию — inline; спавн только под fan-out / настоящую параллельность / изоляцию
> контекста / явную просьбу; модель — по сложности; продолжать через `SendMessage`.

## Как добавить скил

См. `writing-skills`: скопировать `_TEMPLATE/SKILL.md`, написать триггер-`description`
(«Use when …»), заполнить тело (EN для generic-методики, RU для проектных конвенций),
добавить строку сюда.
