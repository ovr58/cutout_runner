# Bug-intake: «баг» → план фикса

Когда пользователь пишет слово **«баг»** (после работы в приложении), сессия восстанавливает
шаги по логу действий и оформляет **отдельный активный план фикса**. Один баг = один план =
одна будущая сессия. **Фикс НЕ исполнять** — эта команда только собирает баг и пишет план.

> Требует, чтобы проект вёл лог UI-действий (jsonl) и файл-курсор последней обработанной
> позиции. Если такого лога нет — заменить шаг 1 на устный разбор шагов воспроизведения от
> пользователя. Пути и маппинг — плейсхолдеры ниже, заполнить под проект.

## Конфигурация (заполнить под проект)

- Лог действий: `{{ACTIONS_LOG_PATH}}` (например `logs/app_actions.jsonl`)
- Курсор: `{{CURSOR_PATH}}` (например `logs/app_actions.cursor`)
- Маппинг `target` → исходный файл: `{{TARGET_TO_FILE_MAP}}`
  (например: кнопка тулбара → `app/main_window.*`; узел дерева → `app/ui/navigation.*`)

## Шаги при слове «баг»

1. **Прочитать от курсора до конца** `{{ACTIONS_LOG_PATH}}` (`tail`/Read с учётом курсора).
   В вывод — ≤50 строк.
2. **Вывести пронумерованный список** действий сегмента (`ts · source · type · target/value`).
3. **Опросить одним сообщением:** по каждому действию — что не так и какое поведение
   ожидалось.
4. **Создать план фикса** `planning/active/bugfix_<slug>_<YYYY-MM-DD>.md`:
   - шапка `Status: ACTIVE (с <дата>)`;
   - **Context** — шаги воспроизведения из лога (по строкам сегмента) + что за компонент;
   - **Баг** — ожидаемое vs фактическое;
   - **Предполагаемые файлы** — по `target` через маппинг `{{TARGET_TO_FILE_MAP}}`;
   - **Набросок фикса** (гипотеза, НЕ исполнять).
5. **Добавить одну строку** в `planning/INDEX.md` (таблица `## active/`).
6. **Сдвинуть курсор** на конец лога (последний `ts`).
