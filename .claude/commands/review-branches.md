# Ревью веток перед мёрджем

Эта команда ведёт **последовательное ревью боковых веток** перед тем, как пользователь апрувит
мёрж в trunk. Канон полос доверия — [`AGENTS.md`](../../AGENTS.md), обоснование —
[ADR-0002](../../docs/adr/0002-trust-lane-by-model-not-host.md). Команда
**Claude-Code-специфична** (управляет выбором модели/эффорта) — зеркала нет.

> **Ревьюером обязан быть Opus.** Ревью веток консервативной полосы — функция доверенной
> полосы. Если ты не Opus — скажи об этом и остановись, не выдавай вердиктов.

> **Жёсткое правило паузы:** перед ревью КАЖДОЙ ветки ты сначала рекомендуешь модель+эффорт,
> просишь пользователя переключиться и **ОСТАНАВЛИВАЕШЬСЯ**. Не начинай ревью ветки, пока
> пользователь не ответит «продолжить». Это нужно, чтобы саму проверку делала уже правильная
> модель. В хостах без переключения модели пауза не запрашивается — там это рекомендация.

## Шаг 0 — собрать и упорядочить список веток

1. Определи trunk: `main`, если есть, иначе `master` (`git rev-parse --verify main || master`).
2. Кандидаты = локальные боковые ветки (или из `$ARGUMENTS`, если задано), **исключая** те, что
   уже предки trunk (`git merge-base --is-ancestor <ветка> <trunk>` → уже влита, пропустить):
   - **консервативная полоса — ревью обязательно:** `feature/*`, `fix/*`, `exp/*`, а также
     `harvi/*` и `claude/*`, произведённые не-Opus моделью (признак — суффикс плана
     `_harvi_` / `_claude_<model-slug>_` в `planning/active/`, либо спроси пользователя);
   - **доверенная полоса — ревью по запросу:** `claude/*` и `harvi/*` от Opus. Они имеют право
     на self-review, но включи их в очередь, если пользователь просил или ветка рисковая.
3. Упорядочи по **таймлайну** — по дате первой расходящейся коммиты, старшие первыми.
4. Покажи обзор очереди: номер, ветка, полоса, число коммитов, `--stat` кратко.

## Шаг 1 — цикл по веткам (по одной)

Для каждой ветки `B` по порядку:

### 1a. Оценить дифф и порекомендовать модель/эффорт

Посмотри `git diff <trunk>...B --stat` и характер изменений, затем выбери из таблицы:

| Характер диффа | Модель | Эффорт |
| --- | --- | --- |
| Косметика: doc/plan-правки, тексты, переименования, мелкий UI | **дешёвая/быстрая** (напр. Sonnet) | низкий |
| Обычный код: сервис/слой данных/новая фича | **сильная** (напр. Opus) | высокий |
| Затрагивает арх-границы проекта (см. `AGENTS.md`), безопасность, миграции БД, релизные ветки | **сильная** | высокий + предложить `/code-review ultra` для крупной/рисковой ветки |

### 1b. Пауза на переключение — ОБЯЗАТЕЛЬНО

Выведи явное указание и остановись:

> Ветка `B` ([N] коммитов, [краткая суть]). Рекомендую: **модель [X], эффорт [Y]** — потому что
> [1 строка обоснования]. Переключи: `/model [X]` (+ при необходимости эффорт), затем напиши
> **«продолжить»**. Если согласен с дефолтом — тоже «продолжить»; «пропустить» — к следующей ветке.

**НЕ продолжай**, пока пользователь не ответит.

### 1c. После «продолжить» — ревью ветки

1. `git diff <trunk>...B` — изучи полный дифф.
2. Проверь **жёсткие архитектурные границы и конвенции проекта** из `AGENTS.md` (слои, доступ к
   данным, изоляция модулей, логирование через логгер, отсутствие секретов в коде/гите).
3. Свериться с планами/тудушками автора ветки: `planning/active/*` + `planning/INDEX.md`.
   Суффикс плана говорит, кто и на какой модели её вёл, — это задаёт глубину ревью.
4. Выдай отчёт по ветке:
   - **Что изменено и зачем** (по файлам).
   - **Нарушения границ/конвенций** (если есть) — с `файл:строка`.
   - **Риски / граничные случаи**.
   - **Что проверить вручную** (сборка, юзер-фейсинг, интеграции). Сборку/тесты сам не запускай,
     если пользователь не просил.
   - **Вердикт:** ✅ мёржить · ⚠ мёржить с правками · ❌ доработать (с конкретикой).
5. Напомни: **мёрж ветки консервативной полосы требует явного апрува пользователя** — твой
   вердикт его не заменяет. После апрува — `finishing-a-development-branch` (verify → merge →
   удалить ветку). Сам не мёржишь, не пушишь и не деплоишь без явной команды.

### 1d. Перейти к следующей ветке → вернуться к 1a (снова пауза на модель).

## Шаг 2 — финал

Когда очередь пройдена — сводка: какие ветки ✅/⚠/❌, что ждёт апрува/правок. Долгие процессы не
запускать, агентов не спавнить без нужды (токен-гигиена, `docs/WORKING_RULES.md`).
