# Ротация `CUTOUT_SECRET` после удаления старой коробки

Status: DONE (выполнено 2026-09-09)

## Context

Старый VPS `<адрес прежней коробки>` удалён 2026-09-09 (план
[`vps-base-tariff-migration_2026-09-09.md`](../archive/plans/vps-base-tariff-migration_2026-09-09.md)),
его диск вернулся в пул провайдера, а `/etc/cutout-runner.env` с секретом на нём лежал. При
переезде секрет намеренно **не** менялся, чтобы откат стоил одной правки A-записи; откат больше
не нужен — долг остался. Запись `planning/BACKLOG.md` B3.

Граница доверия — [ADR-0016](../../../MK/docs/adr/0016-cutout-service-trust-boundary.md) в
репозитории `../MK`: общий секрет в `Authorization: Bearer <секрет>`, две точки хранения —
секрет Supabase (вызывающая сторона) и `CUTOUT_SECRET` в `/etc/cutout-runner.env` на коробке
(`600 root:root`). Сам ADR предупреждает: «появляется вторая точка, где живёт секрет, и её надо
синхронно менять».

**Установленный разведкой факт, влияющий на порядок работ.** В коде `../MK` секрета нет:
`createCutoutRunner` (`supabase/functions/_shared/card-layout/cutout.ts`) вызывается только из
тестов, ни один `Deno.env.get` в `supabase/functions/` не читает секрет выреза. То же признаёт
и ADR-0016 («вызывающая сторона не собрана»). Значит **имя секрета Supabase репозиторием не
задано** — оно известно только владельцу, если секрет уже заведён в панели. От ответа зависит,
нужна ли одновременность правок:

- секрет в Supabase **есть** → правки одновременные, между ними сервис отвечает 401;
- секрета **нет** → одновременность не нужна, коробка правится сразу, а секрет Supabase
  заводится при сборке вызывающей стороны.

Владелец в постановке сессии заявил первое («менять надо в секретах Supabase и в
`/etc/cutout-runner.env`, одновременно»), поэтому план исходит из одновременной смены, но шаг 1
это подтверждает фактом, а не памятью.

## Цель

Сменить общий секрет сервиса выреза на обеих сторонах, не оставив рабочим тот, что лежал на
удалённом диске, и подтвердить смену приёмкой `deploy/README.md` §8 пункт 2.

## Verification

- `curl` без заголовка `Authorization` → `401`.
- `curl` со **старым** секретом → `401` (это и есть доказательство ротации; без него шаг
  выполнен только на словах).
- `curl` с новым секретом и настоящим кадром → `200`, PNG того же размера (`file frame.png
  cutout.png`).
- `sudo stat -c '%a %U:%G' /etc/cutout-runner.env` → `600 root:root`.
- `curl -s http://127.0.0.1:8787/health` после перезапуска → `{"status":"ok","ready":true}`.
- Новый секрет не появился ни в одном файле репозитория: `git grep` по первым 8 символам —
  пусто.

## Что реально сделано

- **Шаг 1 снял главный риск плана и изменил его форму.** Владелец подтвердил: секрет выреза в
  секретах Supabase **не заведён**. Постановка сессии исходила из одновременных правок, но
  одновременность оказалась не нужна — второй точки хранения пока не существует, и правка
  коробки никого не ломала. То же показывал код `../MK`: `createCutoutRunner` вызывается
  только из тестов.
- **Шаг 4 не выполнялся и выполнен быть не мог** — заводить нечего. Действующее значение у
  владельца; вызывающая сторона при сборке берёт его у него, а не из истории.
- Коробка `<адрес коробки>`: новое значение `CUTOUT_SECRET` в `/etc/cutout-runner.env`,
  структура файла не изменилась (сверена построчно с маскированными значениями), права
  `600 root:root` сохранены, `systemctl restart cutout-runner`, `health` → `ready:true`.
- **Резервная копия старого файла удалена** (`shred -u`). Держалась ровно до конца приёмки: по
  ADR-0016 секрет на коробке должен быть ровно один, а мёртвый секрет рядом с живым — тот
  самый «второй, повод для вопроса».
- Старое значение **ни разу не покидало коробку**: проверка «старый больше не работает»
  гонялась там же, значением из локальной переменной. Попытка прочитать его на сторону
  разработки была отбита классификатором — и надобности в этом не было.
