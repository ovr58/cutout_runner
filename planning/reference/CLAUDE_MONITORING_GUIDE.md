# Руководство по мониторингу длительных прогонов для Claude

Инструкция для Claude Code при наблюдении за запущенным длительным процессом (сборка,
парсер, пайплайн, тренировка, деплой). Цель — **диагностировать, не сжигая лимиты подписки**.
Прикладывай в сессии: `@planning/reference/CLAUDE_MONITORING_GUIDE.md`.

## Правила мониторинга (экономия лимитов)

### Перед включением мониторинга
Проведи компакт контекста сессии, если он не пустой.

### Никогда не использовать Monitor
Вместо `Monitor` — `ScheduleWakeup` + чтение файла. Одно уведомление вместо десятков
heartbeat-событий. **Хард-лимит: ≤30 событий мониторинга за час прогона.**

### Интервалы wakeup

| Ситуация | Интервал |
| --- | --- |
| Ожидание старта процесса | 120 сек |
| Стадия активно работает, нет ошибок | 270 сек (в пределах кэша) |
| Подозрение на зависание (нет новых строк) | 180 сек |
| Длительная стадия (>30 мин), всё норм | 1200–1800 сек |

**Про кэш промптов (TTL 5 мин):** 270 с держит контекст тёплым — не платим за промах кэша.
**300 с — худший вариант** (платишь промах, не амортизируя). Если хочется «5 минут» — бери
270 с (в кэше) либо сразу 1200 с+ (один промах окупает долгое ожидание).

### Фильтрация шума при чтении лога
```bash
tail -25 "{{PRIMARY_LOG_PATH}}" | grep -vE '{{LOG_NOISE_FILTER_REGEX}}'
```
Примеры шумных паттернов: `progress|tqdm|heartbeat|Building|downloading` + любые
повторяющиеся «балластные» строки конкретного проекта (списки ID, дампы куки, прогресс-бары).
Всегда фильтровать.

### Алгоритм каждой проверки
1. Читать последние ~25 строк с фильтром выше.
2. Проверить: есть ли новые строки vs прошлая проверка (время последней строки).
3. Искать: `ERROR|WARNING|Exception|Traceback|timeout|failed|{{PROJECT_ERROR_SIGNALS}}`.
4. Сообщить: текущая стадия, последний обработанный элемент, есть ли ошибки.
5. При {{DOMAIN_SPECIFIC_SIGNAL}} → перейти к разделу диагностики (если есть).
6. Перепланировать wakeup, если всё норм.

### Фоновые задачи
- Длительный процесс запускать как `Bash(command=..., run_in_background=true)` +
  `ScheduleWakeup(...)` в одном ходе (харнесс уведомит о завершении — не опрашивать ради опроса).
- На Windows: не `TaskStop` фонового tail-монитора, пока жив bash-родитель (может убить родителя).

## Что докладывать пользователю

**Норма** (раз в проверку, кратко):
```
Статус HH:MM — <стадия> идёт, ~N сек/элемент, ошибок нет.
```

**Немедленно** (не ждать wakeup):
- `ERROR`/`Exception` с трейсбеком;
- стадия зависла: время последней строки > 2× обычного интервала;
- процесс завис / стоп-сигнал не сработал;
- {{PROJECT_IMMEDIATE_SIGNAL}}.

**Только новое:** повторяющийся уже зафиксированный тип проблемы — не дублировать.
Системные сбои (регрессии параллелизма, гонки, отказ соединений) — докладывать сразу.

## Правила применения фиксов во время отладки

### Принцип минимального изменения
- Один баг — одно изменение в одном методе.
- Не рефакторить окружающий код попутно; не добавлять абстракции «заодно».
- Не трогать тесты, если они не сломаны.

### Перед фиксом
1. Прочитать затронутый метод целиком (Read, не Grep-сниппет).
2. Опереть фикс на реальные данные (логи, дампы, воспроизведение), а не на догадки.
3. Проверить легаси-аналог, если он есть.
4. Применить минимальное изменение.
5. Не запускать полный прогон ради проверки — unit-тест или ручное воспроизведение условия.

## Быстрый старт мониторинга (для Claude)

```
1. tail -25 "{{PRIMARY_LOG_PATH}}" | grep -vE '{{LOG_NOISE_FILTER_REGEX}}'
2. Определить: запущен ли процесс (время последней строки свежее ~2 мин).
3. Если запущен — ScheduleWakeup(delaySeconds=270, reason="<стадия> running — periodic check").
4. При wakeup — повторить с п.1. Перепланировать, если норм.
```
Сообщать пользователю только если: ошибка/краш/исключение, зависание (нет новых строк при
активной стадии), или стадия завершилась (started → finished).
