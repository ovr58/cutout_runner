Соблюдать дисциплину затрат лимитов из `docs/WORKING_RULES.md` и раздела «Мониторинг
длительных прогонов» в `CLAUDE.md`.

Ключевое: мониторинг длительных прогонов — только `ScheduleWakeup` + tail+grep (не `Monitor`),
интервал 270 с держит кэш промптов тёплым (TTL 5 мин), ≤30 событий мониторинга в час;
tool-вывод ≤50 строк; действовать при достаточной информации (inline вместо холодных спавнов
субагентов); минимальные правки (1 баг = 1 правка), читать код целиком до фикса; докладывать
только новое, падения — немедленно.

Приоритет — **качество результата**; экономия лимитов тактическая, только где не вредит
качеству. Субагенты — самый дорогой путь (холодный старт + свой поток запросов): не спавнить
ради «тщательности», если контекст уже есть — делать inline; модель субагента ставить по
сложности (read-only поиск/извлечение → Haiku/Sonnet, сложное/критичное к качеству → Opus,
поле `model`); продолжать агента через SendMessage, а не плодить холодные спавны.

**Why:** бюджет токенов и событий ограничен; потери идут от лишнего мониторинга, повторной
работы, раздутых выводов и дорогих субагент-спавнов (100% наблюдаемого расхода — субагент-тяжёлые
сессии).

**How to apply:** перед длинным прогоном — компакт контекста; запуск — `run_in_background` +
`ScheduleWakeup` в одном ходе; на каждый wakeup — одна компактная команда (tail+grep), доклад
кратко, перепланировать.
