# Рабочие правила и затраты лимитов подписки

Дисциплина, с которой Claude работает в этом проекте, чтобы **не сжигать лимиты подписки и
время**. Обязательна. Инструменты мониторинга, специфичные для хоста, — в файле-адаптере
(`CLAUDE.md`, раздел «Мониторинг длительных прогонов»).

Базовый принцип: бюджет токенов и событий ограничен. Потери идут от лишнего мониторинга,
повторной работы и раздутых выводов. Все правила ниже бьют именно по этому.

## 1. Мониторинг длительных задач
- **Никогда `Monitor` для логов** → `ScheduleWakeup` + `tail -N | grep -vE '<шум>'`.
  Одно уведомление вместо десятков heartbeat-событий.
- **Кэш промптов, TTL 5 мин:** 270 с держит контекст тёплым. **300 с — худший вариант**
  (платишь промах кэша, не амортизируя). Хочешь «5 минут» — бери 270 с (в кэше) или сразу
  1200 с+ (один промах окупает долгое ожидание).
- **Интервалы:** старт 120 с · активная стадия 270 с · подозрение на зависание 180 с ·
  длинная стадия (>30 мин) 1200–1800 с.
- **Хард-лимит: ≤30 событий мониторинга в час** прогона.
- **Алгоритм каждого wakeup:** читать ~25 строк с фильтром → diff по времени последней строки
  → grep ошибок → доложить кратко → перепланировать.
- **Не опрашивать ради опроса.** Если харнесс уведомит о завершении фоновой задачи —
  не поллить; ставить длинный fallback-wakeup.

## 2. Дисциплина субагентов, моделей и контекста

> **Стратегически приоритет — качество результата. Экономия лимитов тактическая: пользоваться
> ею только там, где она не роняет качество.** Ниже — где именно не роняет.

Каждый субагент стартует «холодным»: заново выводит контекст, который у тебя уже есть, и гонит
собственный поток запросов — это самый дорогой путь. Поэтому:

- **Действуй, когда информации достаточно.** Не выводить «варианты, которые не будешь делать».
- **Inline вместо холодных спавнов.** Задача с пометкой «тщательно / несколько углов / много
  частей» сама по себе — **не** повод спавнить субагента. Если контекст уже у тебя — делать
  inline своими инструментами.
- **Спавнить только когда это правда лучше по сути:** широкий fan-out-поиск по многим файлам,
  где нужен лишь вывод; настоящая независимая параллельная работа; изоляция большого/шумного
  контекста от основного треда; либо пользователь прямо попросил.
- **Продолжать существующего агента** через SendMessage (контекст сохраняется), а не плодить
  новые холодные спавны на ту же тему.
- **Модель — по сложности задачи субагента.** Read-only поиск/исследование/механическое
  извлечение → дешёвая модель (Haiku/Sonnet). Сложное рассуждение, архитектура, ревью кода,
  всё, что критично к качеству → Opus. Ставить через поле `model` (параметр Agent или `model:`
  во frontmatter `.claude/agents/*.md`).
- **Не докладывать micro-steps.** Группировать находки по сменам фазы.
- **Переиспользовать данные прошлых фаз** (логи уже сделанного прогона), а не запускать заново.
- **Компакт контекста** перед длинным мониторингом, если контекст не пустой.

**Почему именно это:** в наблюдаемой статистике 100% расхода шло из субагент-тяжёлых сессий, а
каждый субагент — отдельный счётчик запросов. Дешёвая модель для простых субагентов и
inline-работа там, где они не роняют качество, — главный рычаг экономии, не трогающий результат.

> Операционализировано в скилах `.claude/skills/subagent-driven-development/` (гейт: inline vs
> спавн, как заскоупить и какую модель) и `.claude/skills/dispatching-parallel-agents/`
> (корректный fan-out только для реально независимых потоков). Эти скилы — прямое продолжение
> данного §2; при сомнении «спавнить ли субагента» сверяться с ними.

## 3. Лимиты вывода инструментов
- Tool-результаты ≤50 строк. Длинные файлы — целевое чтение нужного диапазона, не целиком.
- Запросы к данным — с `LIMIT` / агрегатами, не `SELECT *` без границы.
- Логи — `tail -N | grep -vE 'progress|tqdm|heartbeat|<шум проекта>'`, не `cat` целиком.
- Независимые tool-вызовы — **в одном ходе параллельно**.

## 4. Фоновые задачи
- Длительный процесс: `Bash(command=..., run_in_background=true)` + `ScheduleWakeup(...)` в
  одном ходе.
- Windows-оговорка: не `TaskStop` фонового монитора, пока жив bash-родитель (может убить родителя).

## 5. Минимальные изменения кода
- 1 баг = 1 правка в 1 методе. Не рефакторить «заодно», не добавлять абстракции «на будущее».
- Не трогать рабочие тесты.
- Перед фиксом — прочитать затронутый код **целиком** (Read, не Grep-сниппет) и опереться на
  реальные данные (логи/дампы/воспроизведение), а не на догадки.
- Проверять фикс дёшево: unit-тест или ручное воспроизведение, не полный end-to-end прогон.

## 6. Честная и экономная отчётность
- Падения/зависания/исключения — докладывать **немедленно**.
- Докладывать **только новое**; повторно зафиксированное — не дублировать.
- Не перечитывать только что отредактированные файлы (Edit/Write уже бы упали при ошибке).
- Не повторно выводить уже установленные в диалоге факты.
- Сделано и проверено — заявлять прямо; пропущено/упало — сказать с выводом.

## 7. Необратимое — с подтверждением
- Перед удалением/перезаписью посмотреть на цель; если содержимое противоречит описанию или
  ты это не создавал — поднять вопрос, а не продолжать.
- Внешние/публикующие действия (отправка, пуш, деплой) — подтверждать, если нет устойчивой
  авторизации действовать без спроса.

## 8. Развилки и предтечи планов (backlog)
Когда по ходу работы всплывает **предложение/развилка, которое тянет на отдельный план будущей
сессии** (не делается прямо сейчас) — не терять его в диалоге и не превращать в «варианты, которые
не будешь делать»:

- **Предложи добавить тудушку в `planning/BACKLOG.md`** — отдельный todo-список предтеч планов.
- Запись = **готовый качественный промпт + референсы** (файлы/пути/инструменты/решённая развилка),
  из которого будущая сессия заводит план через `/plan-new`. Пиши промпт так, чтобы он работал
  «холодным» — с явными путями и контекстом, без опоры на текущий диалог.
- Это **дополняет, а не заменяет** уточняющие вопросы: развилка про «что делать **прямо сейчас**» →
  спросить (`AskUserQuestion`); развилка про **отдельную будущую работу** → в backlog.
- При переносе записи в план: `/plan-new` → план в `active/`, строка в `planning/INDEX.md`
  обновлена, запись в backlog помечена `→ заведён план <файл>`. Backlog — пред-стадия перед
  `Draft` в lifecycle планов (см. `AGENTS.md` → «Планы: lifecycle и навигация»).
