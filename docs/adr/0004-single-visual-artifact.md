# ADR-0004: Визуальный слой — один артефакт `docs/VISUALS.md`, переписываемый на месте

- **Status:** Accepted
- **Date:** 2026-08-26
- **Related:** ADR-0003; `planning/reference/SPEC_INTAKE_RESEARCH.md` §5;
  `planning/active/stack-agnostic-init-questionnaire_2026-08-26.md`

## Context

Интейк (ADR-0003) порождает **два** текстовых документа: `docs/TZ.md` («что и зачем») и
`docs/SPEC.md` («как»). Схема главного сценария нужна обоим: из ТЗ на неё ссылается сценарий,
из спецификации — описание модулей. Скриншоты референсов нужны и там, и там.

Разобранные источники этой развилки не решают: arc42 держит схемы внутри своих разделов,
C4 описывает только сами диаграммы, Google design doc просит system-context diagram внутри
раздела дизайна. У всех них документ **один** — вопроса «в каком из двух держать схему» не
возникает.

Варианты, которые рассматривались:

1. **Схема в каждом документе, где нужна.** Отвергнут: две копии одной схемы — два источника
   истины. Через две итерации они расходятся, и никто не знает, какая свежая.
2. **Схемы только в `SPEC.md`, ТЗ ссылается.** Отвергнут: ТЗ читают и не-разработчики, а
   отправлять их в техническую спецификацию за картинкой к сценарию — плохой обмен. И
   референсы («хочу как вот это») — материал ТЗ, а не спецификации.
3. **Отдельный визуальный артефакт, на который ссылаются оба.** Принят.

Отдельная сила — прямое требование пользователя: правку нужно уметь адресовать через схему
(«поменяй на схеме V-03…»), а артефакт должен оставаться **одним результатом без дублёров**.

**Почему дорого откатить:** ссылки вида `V-NN` расходятся по ТЗ, спецификации, планам и
дальше по коммитам. Разъезд версий визуалов обнаруживается поздно — не в момент правки, а
когда кто-то строит по устаревшей схеме. Починка требует аудита всех ссылок, а не правки
одного файла.

## Decision

Весь визуальный слой проекта живёт в **одном** файле `docs/VISUALS.md`.

- **Единственность.** Файл **переписывается на месте**. Файлы-дублёры (`VISUALS_v2.md`,
  `VISUALS_old.md`, `СХЕМЫ.md`, `SPEC_диаграммы.md`) заводить запрещено.
- **Ссылки, а не копии.** `TZ.md` и `SPEC.md` ссылаются на визуал по якорю
  (`[V-03](VISUALS.md#v-03)`). Копия схемы в другом документе запрещена.
- **Стабильные ID.** У каждого визуала ID `V-NN`. ID **не переиспользуется** после удаления —
  снятый помечается в реестре, чтобы старая ссылка не указала на чужую схему.
- **Реестр визуалов** в начале файла: ID · название · тип · что показывает · **кто ссылается**.
  Строка заводится в том же изменении, что и визуал, — по той же дисциплине, что
  `planning/INDEX.md`.
- **Схемы — текстом (Mermaid), не картинкой.** Текст диффится и правится точечно.
  Картинками остаётся только то, что картинкой и является: скриншоты, фото, макеты —
  в `docs/assets/`, имя файла привязано к ID визуала (`v-05-1-<slug>.png`).
- **Синхронная правка.** Изменение визуала обновляет **и** визуал, **и** все ссылающиеся на
  него пункты ТЗ/спецификации — в одном изменении.
- **Уровни C4:** L1 (контекст) и L2 (контейнеры) обязательны для любого проекта, L3 — по
  необходимости, **L4 (код) не заводим**: устаревает быстрее, чем пишется.

## Consequences

**Что теперь обязаны:**

- Любая схема, диаграмма, скриншот референса или макет попадает в `docs/VISUALS.md` и
  получает ID.
- Правка визуала — это правка и ссылающихся пунктов; «поправил картинку» без синхронизации
  считается незавершённым изменением.
- Пользователь может адресовать правку одним ID («на схеме V-03 добавь шаг X»), и этого
  достаточно, чтобы исполнитель нашёл визуал и его зависимости.

**Чего теперь нельзя:**

- Копировать схему в `TZ.md` или `SPEC.md`.
- Создавать второй файл со схемами под любым предлогом («временно», «на сравнение»).
- Класть в репозиторий крупные исходники макетов (Figma/PSD) — вместо них ссылка плюс
  экспортированный скриншот.

**Цена:** одна схема живёт не рядом с текстом, который её использует, — читателю нужен
переход по ссылке. Принято сознательно: цена перехода — один клик, цена разъехавшихся
копий — построенное по устаревшей схеме.

**Границы решения:** это правило про **проектные** визуалы. Диаграмма, поясняющая один
конкретный ADR, остаётся внутри своего ADR — она описывает решение, а не продукт, и вместе
с решением замораживается.
